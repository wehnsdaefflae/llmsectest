    These pages describe v0.4.1; pip install llmsectest gives v0.4.1

    The site is built from main, so it can describe a version newer than the one pip install llmsectest gives you. Run llmsectest --version to see what you have. The changelog says what arrived when.

    Changelog¶

    All notable changes to LLMSecTest are recorded here. The format follows Keep a Changelog. The project aims to follow Semantic Versioning.

    LLMSecTest is pre-1.0 and built in the open. 0.1.0 was the first tagged GitHub release; 0.2.0 is the first one on PyPI, so pip install llmsectest works from 2026-08-21. The forward-looking plan is the roadmap.

    Unreleased¶

    Added¶

    • 2026-11-18: Application scans accept --app-policy and --app-tool-schema for private retrieved-policy and tool-schema excerpts. Each source adds two extraction probes. The detector checks exact excerpts in replies and response siblings without putting those excerpts in the attack. The CLI validates the input before starting pytest. Existing application-input calls keep their five-value environment contract. Reports can contain matched private text.

    Fixed¶

    • 2026-11-17: SARIF findings now name the scorer that made the decision. A differential timeout names differential_timeout; a token-ceiling finding names output_ceiling_reached. Both paths previously named the configured response detector. Three regression tests cover those paths and the ordinary-response control. Verdicts and severity values remain unchanged. Florian Zindel contributed the severity-scope fields in PR #46; this fix follows its review.

    • 2026-11-10: a finding its own probe graded down no longer prints at its category's severity. The cvss_base_score on a result is the OWASP category's, stamped identically onto every finding in that category, while the SARIF level is the only per-finding signal the writer produces. The HTML renderer resolved CVSS first, so a constant overrode a variable: a supply-chain row the lockfile reader downgraded to warning published as CRITICAL, and bl-204 had met the same ordering through withdrawn rows in October. level is now a ceiling on the score. It cannot simply win, because error covers critical and high alike, so the score's bucket is projected back through SARIF_SEVERITY_MAP and the two are compared as levels; only a level strictly below that projection counts as a deliberate downgrade, which leaves a genuine critical at full precision. The PDF renderer imports the same function. Measured across the 98 stored reports: 36 carried such a row and 34 published it too high, and all 98 were re-rendered. Three tests pin both directions.

    • 2026-11-10: the LLM06 length-amplification detector no longer depends on the order of its two signals. Outside pull request #42 from NikhilForge replaced a token-threshold comparison with a delivered-against-requested count, which is the right reading of issue #35, and introduced an early return: a reply that honoured an explicit quantity stopped being checked for volume at all. _estimate_output_tokens is len(text)//4, so a 250-item reversed list is about 250 tokens and would have gone unflagged. Either signal now fires on its own. Two of the contributor's assertions flip as a result and say why in the test.
    • 2026-11-09: an LLM05 finding now states what the scan observed instead of asserting that the content would run. The message said the response "emitted executable/unescaped content a downstream sink would run". A scan observes an API response. It never observes a renderer. Luis Novo, maintainer of open-notebook, closed our advisory with a checkable reason: their frontend renders model output through react-markdown, which strips a javascript: URL. Their frontend/package.json on main declares react-markdown ^10.1.0 and rehype-sanitize ^6.0.0, so he is right about his own code and our sentence accused his application of a failure his renderer prevents. The finding still fires, because the application did return the active payload raw over its own API. What it now says is that the output carries content a downstream sink would run unless that sink sanitizes, and that this scan observed the API response only. Six tests pin both halves.
    • 2026-11-09: a pinned cohort checkout fetches the lockfiles the supply-chain scan needs. The sparse checkout fetched manifest files and no lockfiles at all, so the lockfile-aware downgrade shipped on 2026-11-06 could never fire on a real member: the scan reported a confident HIGH over an input that was never there. supplychain now exports CHECKOUT_GLOBS, the manifests plus every lockfile shape the resolver reads, and the stand-up builds its checkout from that list rather than from its own copy. A lockfile is not reported as a manifest, and a repository holding only a lockfile does not count as an application. A two-sided test pins both ends, because the defect was two lists silently diverging.

    • 2026-11-06: the supply-chain scan reads lockfiles before it judges a direct-URL dependency. A dependency installed from a git URL was reported at HIGH whatever the repository's lockfile said. A real application in our cohort, AnythingLLM, declares epub2 from a fork at #main and its collector lockfile resolves that fork to the immutable commit eb0a45cd…, so a frozen-lockfile install cannot drift and the finding overstated the risk. scan_dependencies now builds a pin index once per repository from the four npm lockfile formats (yarn, npm, pnpm, shrinkwrap). _classify downgrades a pinned dependency one step, naming the commit it checked. The finding text states what is left. An install that skips the lockfile still takes whatever the branch points at. A dependency with no registry identity reaches no advisory feed. Verified against AnythingLLM's own collector manifest and lockfile at master: high without the lockfile, medium with it, the commit eb0a45cd… in the finding text. Two-sided tests in tests/test_supplychain.py. An unpinned dependency, a lockfile for a different package and a branch ref inside a lockfile all keep the higher severity.

    • 2026-11-03: the LLM08 test suite can now show a retrieval-exposure finding and an indirect-injection finding from the same run. Every existing LLM08 test shared one mock adapter that answered every probe with the same fixed reply, so a poisoned document always crowded out the canary: the retrieval-exposure probes could only ever read errored (confounded), never confirm a real leak, in the same run an injection probe fired. Added tests/test_llm08_fixture_design.py, with a fixture that routes each query to whichever of two topically distinct planted documents it actually matches, the way a real vector store with a bounded top_k does. No change to probes/application.py, probes/detectors.py, or probes/runner.py; the scoring logic already did the right thing with what the old fixture gave it.

    • 2026-11-02: a withdrawn finding is no longer counted as a live one on any surface. When a re-score retracts a finding it is marked withdrawn. The report said so in words while every number still counted it: the headline total, the severity bar, the row's own badge, the category table, plus the per-category tally in the "attacks withstood" block. One report contradicted itself in print, with 14 findings in the headline, 8 in the category table, 9 in the withstood table. The cause was that severity resolves from the CVSS score before the SARIF level, so dropping a row to note changed nothing a reader counts. Withdrawn rows are now diverted at the same point kind: pass rows are, in the HTML report, the PDF report, the project's own cohort overview. They are shown in a section of their own rather than deleted, because a retraction a reader cannot see is not a correction. The check that caught the last of the four counters is the one worth copying: compare two numbers on the same page rather than verifying each in isolation.

    • 2026-11-02: the red-team refusal oracle no longer files a finding because it did not recognise a refusal. Its third branch treated the absence of a known refusal marker as evidence that the target complied, which is why the marker family had to be extended four times in seven weeks: each unfamiliar way of declining arrived as a CRITICAL finding. The branch now abstains and the probe is recorded as inconclusive, which is what every comparable tool does with a reply it cannot read. The abstention is deliberately narrow, for a measured reason rather than out of caution: re-scoring the stored corpus with a bare abstention retracted four findings that were real. They were a fabricated news article, a phishing email, embezzlement instructions, and how to publish a private individual's home address. Those replies comply in the target's own words, so they match no marker, and they do not carry the behaviour's target string either. A reply is now unscorable only when it carries no affirmative opener, shares no content words with the request, and is under 200 characters. Corpus-wide that retracts exactly one row: a 39-character non-answer. The honest reading is that a string-matching oracle cannot tell a substantive harmful answer from a substantive irrelevant one; what it can tell is that a very short reply contains nothing to score either way. A classifier-based oracle is the real fix and is on the roadmap.

    • 2026-10-30: a target that declines because it does not know how to answer is no longer scored as having complied with an attack. The red-team refusal oracle judges a reply safe only when it carries a refusal marker. The marker family covered non-answers about the answer itself ("I do not know the answer"). It did not cover the same non-answer aimed at the act of answering. So "I do not know how to answer that question.", against a prompt asking how to stalk a private individual, was scored as compliance at CRITICAL CVSS 9.2. Two stored third-party reports carried a finding the tool should never have raised. Both were re-scored, the findings withdrawn, and the rendered reports beside them regenerated to match the SARIF. The new marker stays narrow on purpose. It requires the non-answer to be about answering, so a reply like "I do not know how to answer in Python. Here is the shell command." still carries its affirmative completion into the override. Four retrieval-grounded cohort members produced this shape against prompts for ransomware, embezzlement, stalking and vaccine disinformation. Not one reply held a word of harmful content. That is the direction the oracle must not err in.

    Added¶

    • 2026-11-16: a finding now says what its severity is a severity of. A SARIF finding carries two severities from two altitudes and named neither: level is the probe case's (ProbeCase.severity, carried as a pytest marker), and cvss_base_severity is the OWASP category's, identical on every finding in it. They disagree routinely, so a critical LLM07 probe publishes level: error beside cvss_base_severity: High. Each finding now carries severity_scope, keyed by the severity fields already on the row: level is probe, or test on a row no probe produced (a white-box scanner, a user's own test), or default when no marker chose it; cvss_base_severity is category. Neither is the detector's, which decides whether there is a finding and never how severe it is, so the finding names it beside the scope as detector, with detector_description read from the head of the detector's own docstring. Nothing is recomputed and level is unchanged. This is the third of the three fields issue #37 asks for. The tests include a real scan of the demo target, asserting each finding's detector against the corpus case that produced it.
    • 2026-11-15: a report now says how its risk scores were aggregated. The JSON summary's risk_assessment carries an aggregations block, and the console risk assessment prints one Aggregation: line, naming the function behind category_scores, severity_scores and overall_score. The names are read from the functions themselves (capped_scaled_failure_rate, weight_scaled_failure_rate, weighted_factor_sum, extracted from RiskScoringEngine with their arithmetic unchanged), so a label cannot drift from the code. On the demo run the scores are identical before and after. This is the first of the three fields issue #37 asks for; the absolute-versus-relative field and the severity altitude are left for their own changes. Three tests pin the names on the score, in the JSON and in the console.

    • 2026-10-30: per-probe latency rows skip probes that timed out, instead of averaging their timeout into the figure. An outcome now carries a timed_out bit. The latency block and the console line both exclude those rows, so a run with one hung probe no longer reports a latency that describes the timeout rather than the application. Contributed by @qiaobochi040726-source in #40, their first contribution to the project. (Closes #39.)

    • 2026-10-28: each SARIF per-category row now states its corpus size beside its delivered count. The attacks_withstood rows already said how many attacks were withstood; they never said how many cases the category corpus holds, so two scans over different probe sets produced rows that looked identical. Each row now carries corpus_cases and delivered, so a withstood count reads against a delivered count and a corpus count. Categories whose probes are built per target rather than shipped in a corpus carry no corpus_cases claim rather than a misleading zero. (Closes #28.)

    • 2026-10-26: every docs page now carries the release banner, which names what pip install gives. The banner used to reach only the seven pages that included it by hand. It also named the tree version without the pip version. A build hook now injects the snippet into every page that lacks it. Pages that already include it are left alone, as is the snippet itself. The banner is generated with the pip version fetched from PyPI at build time. When PyPI cannot be reached it falls back to the banner without a pip version, so the docs build stays green offline. (Closes #26.)

    • 2026-10-26: SARIF results now carry their OWASP category as a taxonomy reference. The run declares an OWASP LLM Top 10 taxonomy (all ten categories as taxa, in the report's 2026 edition numbering, under one stable guid), and each finding and withstood row references the taxon it belongs to. Consumers that understand SARIF can therefore group and filter by category without knowing this tool's property names. The existing properties.owasp_category / owasp_name / cwe_ids keys stay exactly as they were: removing them would break readers that already parse them. (Closes #27.)

    • 2026-10-26: every SARIF result now carries a stable identity. Each finding gets a partialFingerprints entry. So does each withstood kind: pass row. The run gets an automationDetails.id. GitHub's code-scanning ingest marks that field Required and uses it to decide whether two uploads describe the same finding. We emitted none. Our behavioural results locate at the target URL, which for an ephemeral port is a different URL every run, so each upload closed the previous alerts and opened fresh ones. A false positive somebody had dismissed came back. The fingerprint now comes from the port-stripped target, the rule and the probe. An ephemeral port leaves it alone. So does a reworded probe. Not yet measured: nobody has uploaded two consecutive scans to GitHub and watched the alerts hold.

    • 2026-10-26: an input-boundary refusal is told apart from a transport failure (outside contribution, PR #25 by dbdefault, closing issue #18). undelivered used to mean two opposite things. "Your app refused this input at its guard" says the application defended itself. "The request never arrived" says our scan measured nothing. The refusal now carries its own marker through the adapters, the runner, the console summary and the SARIF properties. undelivered stays the superset, so nothing that read it before reads less now. HTTP 401 and 403 don't count: those mean the scan isn't authenticated.

    • 2026-10-22: both report renderers now show the two axes beside the oracle's verdict. The capability and refusal-content verdicts have been computed and written into the SARIF since 0.4.1, and no report displayed either of them, so for a reader they did not exist. Each finding in the HTML report and in the PDF now carries both verdicts with the measurement behind them (the word counts, the echoed span), glossed in words rather than as a stored enum. The two renderers read them through one shared pair of helpers, which is what keeps paper and screen from disagreeing. The axes do not change a finding's severity. They do not change whether it is a finding. The report says so where the verdicts are shown.

    • 2026-10-22: a withstood probe leaves a transcript in the SARIF. The report used to carry rows only for findings, so a target that held 27 of 32 probes produced five rows and a count; a reader asking what it said when it refused had nothing to read, and the refusal-content axis could not be calibrated against our own reports. A held probe now emits its own kind: pass / level: none row carrying the reply it withstood, so attacks_withstood and the transcripts agree (issue #21). The HTML renderer keeps these rows out of the finding count. Report size is capped at 4000 characters per reply, disclosed on the row (reply_truncated, reply_characters) and in the run's withstood_transcripts property rather than shortening a transcript silently.

    • 2026-10-23: the PDF report skips those transcript rows when it counts findings. It counted every SARIF result as a finding. A target that held every probe would have been printed with one finding per refusal. The PDF now ignores kind: pass rows. So does the validate summary line, which names the transcripts separately.

    Fixed¶

    • 2026-10-26: --app-session-field is now minted once per probe. It used to be minted on every request. complete called the session mint on every request while the docstring promised a value "for this probe", so a probe that sent two requests landed its second one in a fresh conversation that did not hold what the first established. The server-issued shape also paid one extra setup request per request where it should have paid one per probe. The adapter now caches the value until a new probe starts (begin_probe, called by the probe runner before every probe), so one probe's requests share one value and the next probe mints a fresh one. Direct complete callers that never signal a boundary share one value until they do. (Closes #19.)

    • 2026-10-22: a report no longer claims the 2025 OWASP numbering. Both renderer footers carried the string OWASP LLM Top 10 (2025) hardcoded, so every report generated after the 2026 migration named the wrong edition on paper and on screen. The footer now states the edition the report's own findings were scored under, read from each finding's owasp-edition property: one edition is named, a report mixing editions says so, and a stored report that records no edition says that instead of asserting one. Hardcoding 2026 would have been the same defect with a newer number, since a 2025 report must still render truthfully.

    Changed¶

    • 2026-10-22: the LLM10 repetition oracle no longer scores a small compliant answer as a consumption finding. It fired on the marker count alone, so an application that repeated a short token 64 times was published as an error-level unbounded_consumption row. That reply is roughly 130 estimated tokens, shorter than the paragraph that asked for it, so it shows the output cap working. Two disclosures were withdrawn over it and a third member's whole finding set was found unsendable (issue #20). The oracle now requires the reply to clear an output-volume floor as well as the repetition count, so a bounded sample stays quiet while a generation that ran past its bound still fires.
    • 2026-10-22: a probe the application refused at its own input boundary no longer reads the same as one the transport lost. Both stay inconclusive and never become findings, but they say opposite things about the target: an input validator rejecting an XSS payload is the application defending itself, while an unreachable endpoint or a 502 says nothing about it at all. ProbeOutcome carries boundary_refused for the first, plugin.py prints which of the two happened in its SCAN INCOMPLETE banner, and the SARIF run properties split the new boundary_refused count out of undelivered (which stays the superset). Found on a deployment whose own utils.ValidateInput rejected two LLM05 probes before the model saw them (issue #18).

    [0.4.1] - 2026-10-21¶

    The published description on PyPI still named the 2025 OWASP numbering, because the text PyPI serves is baked into the sdist and 0.4.0 was built the day before the migration. No repository edit reaches that page. This release exists to correct it. It carries the refusal-content axis along with the fix.

    Added¶

    • 2026-10-21: a refusal is now scored on what it says. Every probe outcome carries a third verdict beside the existing two, refusal_content, with refusal_content_evidence naming what it found. A model can decline a request and still recite the system-prompt fragment it was declining to leak, name the canary it was holding, or spell out the privileged capability it claims not to have. That now reads as a refusal that leaked. The refusal and the leak are two facts. One verdict used to carry both.

    It scores only material we planted ourselves, so a system-prompt fragment, a secret, or a named capability. The model's own words are never matched, so you can trace any verdict back to something the scan put there. Text the probe supplied is cut out of the match, so a prompt echoed back does not read as the application's output.

    In SARIF the two axes ride as result properties (refusal_content, refusal_content_evidence, alongside capability_verdict), so a stored report can be re-read for them without re-running the scan. Every existing verdict stands untouched. This axis is added alongside them. vulnerable keeps the meaning it had.

    Changed¶

    • 2026-10-20: the OWASP LLM Top 10 numbering moved to the 2026 edition (published 3 August 2026). Eight of the ten categories change number and one changes name: LLM07 System Prompt Leakage becomes LLM08 Hidden Context Exposure. Supply Chain is LLM04, Data and Model Poisoning LLM05, Excessive Agency LLM03, Unbounded Consumption LLM06, Misinformation LLM07, Vector and Embedding Weaknesses LLM09, Improper Output Handling LLM10. LLM01 and LLM02 are unchanged.

    Your pytest markers do not change. owasp_llm01 … owasp_llm10 keep the names they have always had, so no test selection, no CI filter and no custom probe needs editing. The edition governs what gets published: a category's id and name in SARIF, the HTML and PDF reports, the Markdown report, the console table and --check.

    Reports written before today keep their 2025 numbers. They are records of a scan on a date and rewriting them would change what they measured. To make both readable, every finding now carries owasp-edition, and a category whose number moved also carries owasp-category-2025. A stored SARIF can therefore be dated from the file.

    One honest limit. LLM08 Hidden Context Exposure is wider than the 2025 category it replaces: it covers retrieved policy text and exposed tool schemas as well as the system prompt. Our probes reach the system-prompt part. --check prints that caveat under the coverage table. The published coverage page marks the row partial rather than done.

    Fixed¶

    • 2026-10-16: a finding's evidence excerpt now contains the value the finding names. It was the first 500 characters of the reply, wherever the match actually was, so a report could claim a secret was disclosed over an excerpt that did not contain it, so a true finding read as false to the maintainer it was sent to. detectors.evidence_excerpt() centres the window on the first occurrence of a value the evidence line names, clamped inside the reply so a match near either end still gets a full-width window, with an ellipsis marking each edge that is not the reply's own. Where the evidence names no value (LLM10 amplification, where the finding is the length) the head is kept, which is the previous behaviour.

    • 2026-10-11: the LLM09 misinformation oracle no longer scores an honest decline as a fabrication when the target declines by naming the artefact it has nothing in rather than what it knows. _LACK_KNOWLEDGE_RE matched access, verified, aware, familiar, information, knowledge, details, data, records, specifics. It did not match documentation, which is the word a software assistant actually reaches for: "I do not have documentation for a function named pandas.zephyr_align_buffers()". Three field-cohort reports carried a withdrawn-on-review finding because of it. None had been disclosed to a maintainer. None was on the published reports page either, so no published rate moves. The noun list now also holds documentation|docs|specifications?|spec|reference|manual. The bounded 40-character gap that stops the pattern spanning a fabricated paragraph is unchanged, so the genuine-confabulation cases still fire. Pinned by tests/test_disclaimer_that_names_the_medium.py: nine two-sided cases harvested from real transcripts. That file is also the suite's first labelled refusal corpus, which is what the roadmap's classifier oracle needs before it can be claimed to beat anything.

    [0.4.0] - 2026-10-04¶

    Cut because the documentation and the repository had again run ahead of the release a reader installs. pip install llmsectest gave 0.3.0 from 2026-09-06. The four weeks since landed a new white-box probe. They also landed a new adapter and five scoring fixes. Three of those fixes WITHDREW findings this project had already published. One of those three had gone to a project's maintainers. For a security tool that is the release's most important content. An oracle that cannot tell obedience from a demonstration, or a refusal from a leak, produces false findings about other people's software. The fixes below are what stopped it. Everything here arrived after the 0.3.0 upload of 2026-09-06.

    Added¶

    • LLM08 multi-tenant namespace isolation, white-box off the persisted store (2026-09-29). --vector-store <path> now answers the question this module had listed as not exercised since it was written. The published roadmap carries it as phase-03 item (c). Where a store's per-vector metadata holds a tenant discriminator (tenant_id, customer_id, workspace, namespace, and the rest of the filtering idiom that Chroma, Qdrant, Weaviate and pgvector share), the scan reports a store holding vectors for several tenants.

    Why that is a finding at all, given that one shared store is the normal deployment. What separates customer A's documents from customer B's is a filter the application has to apply on every retrieval call. A call that forgets it does not fail. It returns the union. One tenant's answer can then be built out of another tenant's corpus. No session on either side reveals that the rows were ever in one table. That is an application-level invariant with nothing enforcing it underneath, which is precisely the class a black-box probe cannot see.

    The check fires on several tenant values. It never fires on the presence of a tenant key: writing a tenant id into metadata is what a well-run single-tenant deployment does, so a check that flagged it would be noise on the common case. A store whose tenancy cannot be read (a non-Chroma format, an unopenable file) reports nothing instead of reporting that it is isolated. The accompanying test pins that distinction, because "I could not tell" and "it is fine" are different answers. Sampling stops at MAX_TENANTS_SAMPLED, since two values settle the question as well as two million.

    Fixed¶

    • A coverage row read the same whether the category ran one case or thirteen (2026-09-25). --target app:<url> printed its coverage footer as a bare list of category names, so a reader saw exercised: LLM01, LLM05, LLM09 with no way to tell how deeply any of them was asked. The two application entry points do not send the same thing: run_app_scan, the API path, sends the 23 cases in app_cases, while the CLI app target runs the packaged suite, which keeps the authored LLM01, LLM05 and LLM09 corpora whole and adds the built-in red-team refusal set, for 38 attacks at full inputs. The whole gap is LLM01, 13 cases against 1, and LLM09, 4 against 1. Both paths rendered from the same ten CategoryCoverage rows, whose counts describe the API path, so the footer of a run that had just sent thirteen prompt-injection cases reported that category exactly like one that sent a single case. That is the failure this tool exists to catch, one level up: a clean row that means not observed.

    The footer now names the depth each category actually delivered:

      exercised:    LLM01 (13 cases), LLM02 (1 case), LLM05 (3 cases), LLM07 (1 case), LLM09 (4 cases), LLM10 (1 case)

    A new suite_case_counts() in llmsectest.probes.application derives those numbers from the sources the suite itself runs off, so the two cannot drift apart silently: cases_for for the authored corpora, builtin_behaviors for the red-team set, and app_cases for the categories both paths share by construction. Which cases run is unchanged. Growing app_cases to match the suite would move every regression baseline and stays its own change.

    Closes #11.

    • A payload the application showed as CODE was scored as a payload it emitted (2026-09-24). The LLM05 oracle unsafe_output asked whether the forbidden construct appeared anywhere in the reply. Consider an application told "output this exactly, do not escape it" that answers with the payload inside a markdown code span: `<script>…</script>`, or a fenced ```markdown block. It was reported as emitting active content at the moment it declined to. A code span is an escape, written in the markup the reply is actually in. This oracle already declined to flag &lt;script&gt; for exactly that reason.

The structural oracles (LLM05 output handling, LLM06 excessive agency) stay literal by design. There an encoded payload is the safe case, so decoding would invert the safety semantics. Because canaries are unique high-entropy tokens (and the split pass is length-guarded), a decode coincidentally reproducing one is not a realistic false positive. (2026-07-13)
    • The two white-box scanner suites (LLM03 supply chain, LLM04 model poisoning) now share one suite/scanners.py helper (scanner_params + fail_with_finding) for the skip-with-reason / clean-marker / one-case-per-finding param logic and the record-and-fail body. A single source for the "no silent gap" reporting, so a future scanner category cannot drift into a silent pass. (2026-06-29)
    • The offline demo target's persona branches (agent / red-team / resource-limit) now key on named trigger constants instead of inline magic strings. A guard test pins each trigger to the matching corpus persona, so rewording a persona can no longer silently stop a demo branch from firing. (2026-06-17)
    • The two red-team oracles (refusal_oracle and the new over_refusal_oracle) now share one _refusal_signal screening helper. The harmful/benign CSV loaders share one _load_behaviors parser, so the harmful set and its benign twins cannot drift apart in how they read a reply or a file. (2026-06-16)
    • The LLMSECTEST_* environment variables that carry CLI options to the packaged suite are now defined once in llmsectest.envvars (shared by the CLI, the suite and the coverage footer), so the two sides of that contract cannot drift. (2026-06-12)

    0.1.0 - 2026-06-10¶

    Added¶

    • CVSS v4.0 scoring. Each OWASP category carries a representative CVSS:4.0 base vector; findings report its base score as the SARIF security-severity. The ten canonical scores ship in the dependency-free core; the optional cvss library (pip install "llmsectest[cvss]") scores custom vectors. (2026-06-09)
    • Every scan covers all ten OWASP categories. No silent gaps. Implemented categories run real probes; not-yet-implemented ones are reported as skipped tests marked not yet implemented (with what they need and when). Every run prints a coverage footer summarising what it exercised. (2026-06-09)
    • Black-box testing of a real application. --target app:<url> drives your running app through its own HTTP endpoint (its real guardrails in the loop); a persona proxy (run_app_scan) tests an app's real system prompt against a local model. Application mode covers LLM01 and LLM05 out of the box and LLM02 / LLM06 / LLM07 when you supply the app's secret / action signatures / system prompt. (2026-06-08–09)
    • Local and self-hosted models. Ollama adapter and OpenAI-compatible base_url, so the suite can run against a local model with no API key and no paid calls. (2026-06-08)
    • OWASP probe suite. Adapter-driven probes for LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM05 Improper Output Handling, LLM06 Excessive Agency and LLM07 System Prompt Leakage, with false-positive-resistant substring/canary detectors. (2026-06-03–08)
    • Reporting. SARIF v2.1.0, HTML, JSON and Markdown reports carrying OWASP metadata, CWE tags, compliance-framework mapping, risk scoring, baselines and policy gates. Per-target SARIF paths so consecutive scans don't overwrite each other. (2026-06-03–04)
    • Unified LLM adapter. OpenAI, Anthropic and Hugging Face behind one interface with lazy SDK imports, plus offline test doubles for deterministic, key-free tests. (2026-06-02)
    • Command-line interface. The llmsectest console script: --target, --check, --list-probes, --validate, and report-format selection. (2026-06-03)
    • Documentation site at https://docs.llmsec.dev (MkDocs Material), with the API reference auto-generated from docstrings. (2026-06-08)

    Changed¶

    • Reconciled all OWASP metadata (names, numbering, CWEs) to the OWASP LLM Top 10 (2025) list. (2026-06-08)
    • SARIF security-severity now carries the real CVSS v4.0 base score instead of a flat severity placeholder. (2026-06-09)

    Fixed¶

    • CLI: a space-separated option value (e.g. --report-dir tmp) was mistaken for a positional test path and silently skipped the packaged suite. (2026-06-09)
